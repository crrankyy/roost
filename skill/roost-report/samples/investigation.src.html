BUG-0001 · fixed by F-073

A keystroke cost grew with the document, and three splices made it flat

ZenithMD's first perf-budget run found that one keystroke on a 2 MB document held the UI thread for 78 ms. F-073 made every per-keystroke step touch only the edited lines, and the same bench then read about 0.27 ms, the same at 1 KB as at 2 MB.

Key findings
  1. A benchmark found it, not a user. F-023's first budget run measured keystroke_to_frame at 133 µs, 7.9 ms and 78 ms for 1 KB, 256 KB and 2 MB (section 2).
  2. Every keystroke did whole-document work. The wrap map rebuilt its tree and row vector on each edit, and the edited line was shaped twice (section 3).
  3. The fix was three splices, landed in 1 h 19 min. Wrap-map tree splice, shape-once handoff to the layout cache, and one-walk anchor resolution; 2 MB went from 78 ms to about 0.27 ms (section 4).
  4. Profiling the fix found the next bug. The Stage 1 parse worker sat at 100% in ts_tree_edit even at 1 KB (BUG-0002, fixed 29 minutes later); set_width is still O(lines) (section 5).

How it was found

The cost grew in step with document size

The bug was a number in a bench log. The budget is 5 ms per keystroke for files up to 2 MB, from Architecture §7.

Cause

Three steps of every keystroke did whole-document work

F-073's spec names the causes. Each one scaled with the document, not with the edit.

F-073 feature.md · ObjectiveWrapMap::edit rebuilds its segment list, allocates a String per line to compare it, relocates every row and rebuilds the whole SumTree and flat row vector on every edit; the controller then shapes the edited line a second time through LayoutCache (DEBT-0011) and allocates each visible row's text while building the frame. Anchor resolution maps each anchor through every logged transaction (DEBT-0013).
  • The wrap map rebuilt itself. Reshaping one line took 11.89 ms on a 10k-line document because the tree and row vector were rebuilt around it.
  • The edited line was shaped twice. WrapMap shaped it, then LayoutCache shaped it again (DEBT-0011).
  • Anchors walked the whole log. Each anchor was mapped through every logged transaction: 3.16 ms for 1,000 anchors (DEBT-0013).
Fix

Each step now touches only the edited lines

F-073 split the work into three tasks, one commit each, and logged bench medians after each.

78 ms became about 0.27 ms, flat across sizes

After T-073.2 the keystroke bench read 216–270 µs at 1 KB, 267–405 µs at 256 KB and 268–291 µs at 2 MB: "Cost now flat in document size."

The wrap map splices instead of rebuilding

T-073.1 turns edits into line deltas and shapes only the new lines. Excerpt of WrapMap::edit: the old body walked every segment and re-checked every line; the new one is three calls.

crates/zmd-display-map/src/wrap.rsfeae721 · excerpt
    pub fn edit(&mut self, fold: &dyn FoldLayer, edits: &[ByteEdit], shaper: &dyn LineShaper) {        let mut segments = self.segments();        for edit in edits {            apply_edit(&mut segments, edit);        }        let old_lines = std::mem::take(&mut self.lines);        let new_count = fold_line_count(fold);        …  (a loop over every segment, comparing each line's text)        let regions = merge_edits(edits);        let deltas = self.line_deltas(fold, &regions);        self.edit_lines(fold, &deltas, shaper);    }

Source: git show feae721. The "…" line stands for the rest of the deleted loop, left out here.

The controller hands shaped lines to the cache

T-073.2 stops the second shaping: lines the wrap map just shaped go straight into the layout cache.

crates/zmd-app/src/editor/controller.rsaef46c8
        self.display.edit(&snapshot, edits, self.shaper.as_ref());        self.cache.apply_edits(snapshot.clone(), edits);        // The wrap layer just shaped the edited lines (post-edit numbering); handing them to        // the cache after `apply_edits` dropped the stale ones saves shaping them twice.        for (line, rows) in self.display.wrap().shaped_lines_since_edit() {            self.cache.insert_shaped(*line, rows.clone());        }        self.last_stage1_request_version = snapshot.version;        self.stage1.request(snapshot, edits);

What's left

One cost is still O(lines), and nothing guards the budget yet

Each item is named in F-073's or F-023's as-built follow-ups.

Open · DEBT-0009

set_width still re-wraps every line. It took 28.88 ms on 10k lines after the fix; F-073 left it out of scope on purpose ("every line re-wraps anyway").

Caveat

The perf gate has never run. F-023's as-built says: "The workflow has never run on GitHub: no perf runner exists." A regression back above 5 ms would not be caught in CI.

Caveat

The remaining frame cost is logarithmic, not zero. The T-073.2 profile puts 25–30% of build_frame in sum-tree cursor allocation in row_layout/pixel_y, plus rope get_line.

Resolved · BUG-0002

The parse worker no longer falls behind. Found while profiling this fix, it was resolved the same morning in b2b2487 as part of F-014.
