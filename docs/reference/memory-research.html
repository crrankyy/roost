How Lynx should remember

Don’t adopt a memory framework. The plan’s direction holds: keep every message, compact older turns, search history, keep a list of facts. The research changes six parts of it, and every infrastructure change it needs is free.

1

Facts live in their own table

With keys and versions. Summaries never hold facts, because repeated summarising loses them.

2

Background work runs in batches

One cheap call every few thousand tokens or after idle time writes notes and proposes fact changes. Not a call after every turn.

3

An observation log replaces day summaries

Dated, prioritised notes that are appended rather than rewritten, each linked to the messages it came from.

4

The overall summary is rebuilt from parts

Each night from facts and older notes, never by re-summarising the previous summary.

5

Things that change every turn go last

The time and search results sit at the end of the prompt, so the provider can reuse its cache of the start.

6

Search results only when the match is strong

Word-for-word history is the main thing searched, and results are added only when the top match clearly wins.

The three named sources

What each one does, how it would fit Lynx, and what to take from it.

Mastra memory

TypeScript · Apache-2.0 · an agent framework with four kinds of memory
Borrow the design
KindWhat it does
Message historyThe last N messages.
Working memoryA Markdown block (or typed object) the agent updates with a tool, shared across one user’s threads.
Semantic recallEmbeds every message and retrieves the top matches plus neighbours each turn. Adds latency every turn; the local embedder truncates at 512 tokens.
Observational MemoryMastra’s recommended option. Background agents turn old messages into a dense, dated log.
How Observational Memory works
  • Observer: once unobserved messages pass a threshold (30k tokens by default, buffered every ~6k), writes dated, prioritised notes. Each note can carry the date observed, the date it refers to, and a relative date.
  • Reflector: once the log passes 40k, rewrites it, merging related notes and dropping superseded ones.
  • Raw messages leave the context once observed but stay stored, with links from each note group back to them and a recall tool.
  • Cache-friendly: the log is only appended to between reflections, so the start of the prompt stays the same.
Reported results (LongMemEval, by Mastra)
Observational Memory, gpt-5-mini94.87%
Observational Memory, gpt-4o84.23%
Retrieval, top 20, gpt-4o80.05%
Zep, gpt-4o71.20%
Full history in context, gpt-4o60.20%

Text compresses roughly 3–6×.

For Lynx
  • The closest match to one continuous chat. Copy the observer and reflector design, scaled down: its defaults assume 128k-token models.
  • Don’t install the package. It is tied to Mastra’s agent class and the AI SDK, so it would replace Lynx’s chat engine.
  • The reflector rewrites its own output, which is the repeated-summarising risk. Lynx avoids most of it by keeping facts in their own table and keeping links to source messages.

Honcho

Plastic Labs · Python server (AGPL-3.0) · TypeScript SDK (Apache-2.0). The linked BunsDev repo is a 3-star fork of plastic-labs/honcho.
Borrow ideas
How it works
  • Models people, not conversations: every participant is a “peer”.
  • A background worker reads every message and extracts explicit conclusions (things the person said) and deductive ones (with their premises).
  • A “dreamer” consolidates and finds patterns across messages; peer cards hold core biographical facts; summaries every 20 and 60 messages.
  • Each peer can hold its own view of another, built only from what it saw. A chat endpoint answers plain questions about a person.
Why not run it
  • Python, a separate worker, Postgres with pgvector, optional Redis.
  • Model reasoning on every message, which doesn’t suit a small budget.
  • AGPL server; the README describes self-hosting as for testing and evaluation.
For Lynx
  • Mark each fact as said or inferred, keep an inferred fact’s premises, and never present an inference as something you said.
  • An “About you” card, rebuilt in the background.
  • Each helper sees only the facts its task needs, like Honcho’s per-peer views.

ReasoningBank

Google Research · ICLR 2026 · Python demo, “not an officially supported Google product”
Later, with tools
How it works
  • Memory of strategies, not facts. After each task a model judge labels it a success or a failure.
  • Lessons (title, one-line description, content) are distilled from both, retrieved by similarity into the system prompt, and simply appended.
  • MaTTS runs extra attempts per task to produce contrasting lessons.
Reported results
  • WebArena success up to +8.3 points over no memory (Gemini 2.5 Pro 46.7 → 53.9; 56.3 with MaTTS).
  • SWE-Bench Verified 34.2 → 38.8 (Gemini 2.5 Flash), with fewer steps per task.
  • Learning from failures helped (46.5 → 49.7), even with a judge only ~72.7% accurate.
For Lynx
  • It’s about agents getting better at tasks, not remembering you. Relevant once helpers do work with tools.
  • Plan a lessons table per helper, written by a judge-and-distil step batched nightly, and pulled into that helper’s instructions.
  • Skip MaTTS: it multiplies model calls.

TencentDB-Agent-Memory

Extract facts every 5 conversations or after 10 minutes idle, at most 20 per pass. Every layer links down to raw evidence. Automatic recall has a timeout and a size budget.

engram

A topic key turns a save into an update. Hash dedupe. On save, show similar entries so the agent decides. Review-after dates per kind of fact; soft delete.

Graphiti, Hindsight, Letta

Facts carry “valid from” and “invalid at” dates. Standing answers refreshed in the background. A few small blocks always in context that the agent edits with a tool.

Design rules from the papers and write-ups

Twelve rules, each with the evidence behind it. Results are as reported by each source.

1Facts are records, not summary text

One summary at 36.7× compression kept 40% of 2,000 facts. Three rounds of compaction lost 53% of 20 project rules, across Claude Sonnet 4.5 and 4.6, Opus and GPT-5.4. Nothing was made up; the model said the information was gone.

Facts as First Class Objects
2Key facts by subject and attribute, and version them

A new value supersedes the old one, which stays retrievable. Embeddings picked the right one of several near-identical facts only 20% of the time, so exact key lookup has to sit beside vector search.

Graph-Native Cognitive Memory, Graphiti, engram, Facts as First Class Objects
3Check facts when they’re used; don’t delete by decay

Copilot cites a source for each memory and refreshes it when confirmed (merged pull requests 90% vs 83% in an A/B test). MemArchitect’s decay-based pruning cost 20–45 points on single-detail and time questions, because facts mentioned once were removed. A personal agent has to keep a birthday you mentioned once.

GitHub Copilot memory, MemArchitect
4Turn relative dates into absolute ones when extracting

The biggest gain was on time questions (+16 points). The graph walk added only +1.2 points over plain retrieval, so skip graphs.

GAAMA
5Build the prompt deterministically, within a budget

Pinned items first. Extract facts before anything is compacted. Keep “no match” distinct from “error”.

ClawVM
6Batch the background work

Extraction every few turns or after idle time, and a nightly compile-and-check pass, instead of a call after every turn.

TencentDB-Agent-Memory, LangChain on continual learning, claude-memory-compiler
7Facts from tool content need approval

A fact taken from an email or web page could be planted, so it waits for you. LangChain also found the extraction prompt is most of the work, and that agents add specifics instead of generalising.

LangChain Agent Builder
8Word-for-word retrieval is strong and cheap

MemPalace: 96.6% R@5 on LongMemEval with no model calls. agentmemory: keyword search alone 86.2%, with embeddings 95.2%. ByteRover: keyword search only, 92.8%. All self-reported.

MemPalace, agentmemory, ByteRover
9Put what changes every turn at the end of the prompt

A change invalidates the provider’s cache for everything after it, so the time and search results go last.

Anthropic prompt caching and compaction docs, headroom
10Don’t rely on the model to decide when to compact

In LangChain’s experiment the models almost never triggered compaction. The Focus paper (5 tasks) needed forced compression to save tokens. Keep token-threshold triggers.

LangChain autonomous compression, Active Context Compression
11With tools, search returns snippets and a separate read expands one

74.1 vs 52.8 for basic retrieval at a similar token cost.

A-RAG
12Cap always-on memory and tidy it periodically

About 1–1.5k tokens of always-on memory, cleaned up by a regular pass, instead of an ever-growing instruction block.

OpenAI on harness engineering, Anthropic on context engineering

Recommended design

Everything lives in lynx.db, so Litestream’s backups already cover it.

Data

TableHolds
messagesEvery message, forever. Exists today. The source of truth for what was said.
messages_ftsFull-text index over each message and its reply.
observationsDated, prioritised note groups, each with the range of messages it covers.
reflectionsCondensed versions of older note groups, linked to the groups they replace.
factsOne row per version: key (user.timezone, person:arjun.role), value, kind, said or inferred or from a tool, source message, valid from and to, last confirmed, pinned, status, review date. A new value supersedes the old row, so Settings can show history and undo.
memory_runsA log of what each background run read, wrote and cost.

Writing memory

  • During a turn: no extra calls.
  • Observer batch, one cheap call, when unobserved turns pass ~8k tokens, after ~10 minutes idle, before /fresh, or straight away on “remember that…”.
  • It gets the new turns, pinned facts and similar existing facts, and returns a dated note group plus fact operations (add, supersede, confirm), each with its source message. Code applies them; facts from tools wait for approval.
  • Nightly pass, one call: reflect older notes, generalise specific facts into rules, flag contradictions, rebuild the “About you” card and the overall summary from facts and reflections.

At about 50 turns a day: 4–6 observer calls plus 1 nightly call.

Stack and infrastructure, all free

Only model calls cost money. Nothing here needs a paid plan or a new server.

NeedRecommendationNotes
Full-text searchSQLite FTS5Built into node:sqlite; tested working on Node 22.23 (SQLite 3.53.4). Confirm on the server’s Node 24.
Vector search, latersqlite-vec 0.1.9MIT or Apache-2.0, with an ARM64 Linux build on npm. Needs allowExtension: true and loadExtension() (Node 22.13+). Pre-v1, so expect changes.

Background modelTry Workers AI qwen3-30b-a3b-fp8A 6k-in, 800-out call is ~52 neurons, so ~190 calls a day fit for free (shared with embeddings). Judge it on the eval; fall back to GLM 5.3 Flash. OpenRouter’s free models allow 50 requests a day, and their providers may log prompts.
Prompt cachingOpenRouter session_idZ.AI caches GLM automatically (writes free for now, reads ~0.2× input). Send a fixed session_id, never pin a provider, keep the prompt start identical, and log cached tokens. Stickiness ends after 10 minutes idle.

Build order

Start with the test, so every later step can be measured.

  1. 0

    Eval first

    A scripted multi-day conversation with planted facts, a changed fact (dentist moved from 3pm to 4pm), preferences, rules and time questions. Score each category, track cost per day, and rerun on every change. LongMemEval’s public questions can also be sampled.

  2. 1

    The server builds the context

    Observer batches, the observation log, the keyed and versioned facts table, /fresh, and the new prompt order. Replaces “last 40 messages”.

  3. 2

    Full-text search

    Strong-match results added at the end of the prompt, plus session_id and cache logging.

  4. 3

    Nightly pass and the memory list

    Reflections, the “About you” card, contradiction checks, and a memory list in Settings with history and undo.

  5. 4

    Embeddings and sqlite-vec

    Only if the eval shows keyword search missing things.

  6. 5

    With tools

    remember, recall and read; lessons per helper.
